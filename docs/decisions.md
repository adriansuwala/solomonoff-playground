# Decisions

Numbered so code comments can cite `D3` without a URL. Each records the rejected
alternative and what it would have cost.

---

## D1 — Vendor the authors' figure data; do not fetch it at build time

**Decision.** Copy `acowsik/self_play_pretraining` at commit `2c25ed6` into
`vendor/spp/` and commit it.

**Rejected.** Downloading from GitHub in a build step or at app runtime.

**Cost of the alternative.** The app would break whenever the upstream repo
changes, and every reader would need network access to see a number. The
upstream repo has exactly one commit today, so drift is unlikely — but the
experiment is free and removes the dependency entirely.

**Consequence.** 50 MB of vendored data in the repo. `.gitattributes` marks it
`linguist-vendored` so blame and diffs point at the build.

---

## D2 — Derive published numbers; never transcribe them

**Decision.** Every number the app shows is recomputed from shipped data by
`tools/build_data.py`, using the authors' own algorithms. Where a value cannot
be derived, the build fails rather than falling back to a literal.

**Rejected.** Typing the paper's tables into a Python constant and rendering
them.

**Cost of the alternative — measured, not hypothetical.** Extracting Table 5
from the PDF produced rows with **nine values against seven column headers**,
with `last_step` and `negate` misaligned. A transcription would have shipped
wrong numbers with a paper citation attached, and the citation would have made
them *more* credible, not less.

**Consequence.** `tools/verify_data.py` re-derives and diffs against the
authors' committed `.tex` artefacts (134 checks). A hand-maintained literal has
no such gate, which is the whole point.

## D3 — Table 2 comes from `frontier_traj_perk.json`; Figure 2 comes from the CSVs

**Decision.** Keep both sources and label which claim each one backs.

**Rejected.** Using the fig2 CSVs for everything, since they carry all three
arms in one shape.

**Cost of the alternative — measured.** Computing all ten Table 2 exponents from
`frontier_traj_perk.json` reproduces the paper exactly. Computing the same ten
from the fig2 CSVs does not:

| corpus | paper | traj JSON | fig2 CSV |
|---|---|---|---|
| text (dclm) | 0.123 | **0.123** | 0.080 |
| DNA (8-symbol) | 0.435 | **0.435** | 0.243 |
| audio 8-bit PCM | 0.260 | **0.260** | 0.241 |
| MIDI (Mutopia) | 0.249 | **0.249** | 0.186 |

The CSVs are per-K trajectory slices with fewer seeds behind some points, so
their frontiers differ. Using them for Table 2 would have produced a table that
looked plausible and was wrong on every row.

**Consequence.** `scaling.json` has a `ladder` block (Table 2, Figure 1) and an
`arms` block (Figure 2). They are never mixed.

## D4 — TypeScript + React + Vite; hand-rolled SVG charts

**Decision.** React 18 with Vite, strict TypeScript, and `d3-scale`/`d3-shape`
for scales and paths only. No charting library.

**Rejected.** Recharts, Plotly, visx, or plain JavaScript.

**Cost of the alternatives.** A charting library would need a custom layer
anyway for the log-log compute axis, the fitted-curve overlay, and the frontier
highlighting — and would hide the axis definition that makes a point traceable
to the paper. Plain JavaScript was ruled out by the operator.

**Consequence.** Chart components own their axes explicitly. `src/lib/scales.ts`
holds the log-log compute scale and is unit-tested against the paper's axis
range.

---

## D5 — Interactive scoring runs against precomputed results, not live inference

**Decision.** The app displays results computed by `tools/measure_local.py` on
this machine, plus the authors' released numbers. It does **not** load model
weights in the browser.

**Rejected.** Converting the released PyTorch checkpoints to ONNX/WebGPU and
running them client-side.

**Cost of the alternative.** The 100k rung is 98,496 parameters and would run,
but the interesting rungs do not fit a browser download budget, and a
client-side inference path would need its own correctness argument against the
same checkpoints. The measurements that make the app's claims checkable are
cheap to precompute and cheap to re-run.

**Consequence.** `local_measurements.json` is regenerated by a documented script
and carries its own provenance block (host, torch version, thread count). The UI
labels these as *our* measurements, distinct from the authors'.

---

## D6 — Every claim carries a paper section reference

**Decision.** Section references are a typed field (`PaperRef`) on every claim
object, resolved against `SECTIONS` in `tools/paper_refs.py`. A reference that
does not resolve fails `verify_data.py`.

**Rejected.** Prose references sprinkled through component copy.

**Cost of the alternative.** Prose drifts silently and cannot be checked. The
operator asked for section references on all claims, and a machine-checked link
is the only version of that which stays true as the app grows.

**Consequence.** `src/components/PaperRef.tsx` renders them; nothing displays a
number without one.

## D7 — Converge the power-law fits; do not ship SciPy's default tolerance

**Decision.** `tools/build_data.py` calls `fit_curve_power_law_with_floor` with
`FIT_TOLERANCES = 1e-14`, overriding SciPy's default `ftol = xtol = gtol = 1e-8`.
The vendored function gained a keyword-only `tolerances=None` parameter that
defaults to the upstream call, so the vendored code still behaves exactly as the
authors' unless this build opts in.

**Why.** The default stops the optimiser when the cost stops *moving*, not when
it reaches the optimum, so the returned parameters are partly a property of the
machine. Measured on `aitdcc_d_glibc_rand`: sweeping the tolerance moves the
fitted amplitude by 4.4e-5 (1e-8 → 1e-10) and 6.5e-6 (1e-10 → 1e-12), settling
to 3e-12 between 1e-14 and 1e-15. In other words the default answer sat ~5e-5
from the true optimum while the bundle stored it to 17 significant digits.

That under-convergence is what made the build machine-dependent. SciPy's
manylinux wheels bundle OpenBLAS, which selects a kernel at runtime from the CPU
feature set, so the arithmetic path differs between the generation machine and
a GitHub runner. Two CPUs running identical pins disagreed by up to 1.4e-5 —
inside the 5e-5 convergence error, which is why it looked like inexplicable
noise. Converging the fit removes the dependence: the answer is now the
mathematical optimum rather than a stopping artefact. The inputs are already
bit-identical across hosts (compute is integral, losses are CSV-parsed), so once
converged there is nothing platform-dependent left to disagree about.

**Rejected.** Loosening the CI tolerance to cover 1.4e-5. That treats a
measurement error as an acceptable result and leaves 17 digits of false
precision in a published artefact. Rounding the stored values instead. That
reduces the noise but does not make the value *right* — the number would still
be 5e-5 off the optimum.

**Cost.** The vendored file is no longer byte-identical to the authors'. The
addition is additive, keyword-only and defaults to upstream behaviour; the
docstring says so in place.

**Consequence.** `scaling.json` is regenerated: 166 leaves move (111 amplitude,
37 floor, 18 alpha), the largest by 3.8e-3 relative. `alpha` and `floor` are
stored rounded to 5 decimals, so 52 displayed values shift in the 5th decimal.
Nothing in the repo hardcodes them — pages read from the bundle — and
`verify_data.py` still passes 165/165. CI's reproducibility gate
(`tools/diff_bundle.py`) stays in place as a net, at `rtol=1e-6`: now roughly
four orders of magnitude above the residual CPU noise, and still tight enough to
catch the ~1.4e-6 drift a scipy bump introduces.
